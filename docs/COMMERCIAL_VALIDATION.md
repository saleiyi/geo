# 首单验证：面向建站与 SEO 服务商

这是一份待执行的验证方案，不是客户、需求或收入证明。初始状态：已访谈 0 人、已接收真实试用 0 家、已付费 0 家、收入 0；所有意愿和定价假设均未验证。若后续有真实记录，应按证据更新，不从产品功能或测试通过率推导商业结论。

首批对象选为**替客户建设或优化小型网站的独立服务商、小型建站工作室、SEO 服务商**。他们需要实际负责一次优化交付，能提供获准分析的公开网页，并愿意在修正后提供复测证据。先聚焦有近期交付任务的人，不要求对方已经在销售 GEO 服务。

当前待验证的用途：用免费单页完整报告发现可核对的问题，保存首次报告为基线，修复后复测同一页面，整理成客户看得懂的前后交付证据。基线复测已通过本地功能验收（见 `CONVERSION_V2.md`），尚无真实客户试用。工具检查服务器返回的 HTML，不运行 JavaScript；报告及差异不证明全站表现、Google 排名或真实 AI 引用。

## 要验证的四个假设

| 假设 | 应观察的证据 | 不能当作证明的信号 |
| --- | --- | --- |
| 优化交付证据是实际工作中的问题 | 对方展示上一份脱敏交付，说明证据如何制作、哪里耗时 | “这个想法不错” |
| 单页报告与基线复测能用于真实任务 | 使用获准页面完成修复和同页复测，向真实客户交付或纳入实际工作记录 | 只浏览演示、只保存截图 |
| 带来的价值超过采用成本 | 有记录的交付工时、复核负担和支持成本，并与对方现有流程比较 | 没有计时依据的“节省很多时间” |
| 存在可付费的后续服务 | 对方提出具体付费范围和预算，最终发生真实付款；后续任务继续使用 | 点赞、口头愿意、预约、没有支付的意向单 |

## 第一轮怎么做

1. **先验收自己的交付流程。** 用获准测试页面完成扫描、保存基线、修复一项确实存在的问题、复测和导出。确认页面、检查标识、证据及规则版本可对齐；不兼容版本必须明确标记。准备一份匿名演示，标为“演示”，不可当成客户案例。
2. **手工建立一个小名单。** 用户目前没有客户资源，可从服务商自己的公开服务页面、作品集、商业联系渠道，以及允许相关交流的行业社群开始。记录为什么该对象符合目标，不购买名单，不批量抓取私人联系方式。第一批暂定 10 个合适对象作为执行范围，这个数字不是需求证据，也不是成功标准。
3. **由用户逐条发送邀请。** 使用下面草稿，根据对方公开业务加一句具体背景。先邀约了解真实交付，不推销“提高 AI 引用率”。遵守所在平台规则；对方拒绝则停止，没有许可不增加邮件订阅、不公开其名称。这里仅提供草稿，不执行发送。
4. **先访谈，再邀请真实试用。** 记录五个问题的具体回答和可核对材料；得到同意后选一份近期实际任务。对方没有任务或不能提供获准页面时，记录原因，不编造替代数据。
5. **以一项实际修复完成免费试点。** 由对方决定并执行网站修改，保留前后事实。收到反馈后确认：报告是否进入交付、是否要在下一次任务继续用，以及采用成本有哪些。
6. **仅在明确了用途后讨论下一笔交易。** 免费完整扫描与复测报告保持公开承诺。付费讨论围绕额外工作，例如人工复核、交付建议或实际优化实施；范围未确定、功能未实现时不可当作已有套餐销售。

没有正式托管环境时，可以先访谈、展示明确标注的演示，或在征得同意后手工交付报告。可公开使用的网址、服务账户、平台条款和费用、隐私联系人及支付方式仍是上线依赖，不把它们写成已落实。不得为推进本方案擅自购买域名、开通付费服务或向他人发送消息。

## 访谈提纲：五个问题

每题优先询问最近一次真实经历，允许对方不透露客户身份。需要展示资料时先脱敏；记录原话、日期和证据位置，不把自己的解释写成对方原话。

1. **上一份真实交付：** 最近一次为小网站完成优化交付是什么时候？你向客户交了什么，怎么证明修改确实发生？如果方便，能否展示脱敏后的某一页交付材料？
2. **频率与下一次任务：** 这类交付在你最近一个月出现过几次？下一次已确定的任务是什么，哪一步会需要前后对照？没有则如实记“没有”。
3. **现有替代方式：** 上一次你用了哪些工具或手工步骤来扫描、判断、复核和出报告？哪些结果还要自己解释，什么会让你不想换流程？
4. **真实工时与成本：** 上一次从第一次检查到客户拿到报告，各环节大约花多久？哪些有计时或项目记录，哪些只是估计？工具、沟通与返工成本分别是什么？
5. **试用决定：** 对下一份已确定的任务，你愿不愿意用一个获准公开页面做免费试点，并在一次真实修复后回传前后证据？如果愿意，谁负责、什么时候做、什么结果才算能用；如果不愿意，主要原因是什么？

对方完成真实试用后，再问预算：**“你通常为这部分工作安排多少预算？如果让我为下一次交付提供你刚才说的额外服务，你会怎样定范围、谁决定采购、认为合理的预算是多少？”** 不暗示必须接受某个价格；尚未确认的口头报价只记为假设。

## 英语邀请草稿

仅供用户人工复制、个性化后发送。方括号为待填写内容；不要放入未经核实的客户数量、效果或收入。

```text
Subject: A small website handoff question

Hi [Name],

I saw that you help clients with [specific website/SEO service shown on their public page]. I'm testing a workflow for people who improve small client websites: a free, complete single-page HTML audit, followed by a same-page retest against a saved baseline.

The goal is to make the evidence behind a client handoff easier to prepare. It does not measure search rankings or actual AI citations.

Would you be open to a short conversation about your last optimization handoff—what you delivered, how you checked it, and what took time? A redacted example would be helpful if you are comfortable sharing one.

If it fits a current task, we could then try a free pilot on one public page you are authorized to submit, make one real correction, and review the before-and-after evidence. There is no paid commitment for that pilot.

If this is not relevant to your work, no problem.

[Your real name]
[Real contact or working product link, if available]
```

Se fizer sentido para um trabalho atual, podemos testar gratuitamente uma página pública que você tenha autorização para enviar, aplicar uma correção real e revisar as evidências de antes e depois. Esse piloto não envolve compromisso de compra.

## 免费试点的验收约定

邀请被接受后，用文字确认以下内容。获准分析页面不代表获准修改网站，也不代表获准把对方做成公开案例。

| 项目 | 试点前确认 | 验收证据 |
| --- | --- | --- |
| 任务与权限 | 参与者有权提交该公开页面；确认谁能批准和执行修改 | 同意记录、页面 URL、参与角色；避免敏感查询参数 |
| 首次扫描 | 完整报告，保存原始基线；标明页面、日期和规则版本 | 原始 JSON / Markdown 或相应导出文件 |
| 实际问题 | 双方认可一项具体问题和修改目标 | 修改前证据，例如缺失的描述、错误 canonical 或无意的 noindex |
| 修改 | 由获授权者执行、记录修改内容和上线时间 | 对应 HTML / 配置差异或可核对的页面证据；不以空泛评分目标代替修复 |
| 同页复测 | 扫描同一页面；核对 URL、规则版本和可比检查 | 复测报告、差异报告、该项检查前后状态和证据 |
| 不可比情况 | 规则变化、页面跳转或抓取失败须明确 | 标记不可比 / 待确认，不把缺证据当作已修复 |
| 交付结果 | 对方说明报告实际如何使用 | 已交付的脱敏材料、实际使用反馈；未经许可不公开 |
| 采用成本 | 记录本次操作、复核、支持所花时间 | 实测时长与估算分别标记，记录困难和返工 |

通过标准是完成**至少一项真实、获授权的修改，并取得可核对的前后证据**。报告未能证实修复时，如实记录失败或未知，保留原因。完成免费试点只验证交付流程可用，不等于验证了付费意愿。

## 付费假设与首单

当前不填写未经验证的价格，不把免费功能包装为已有付费套餐。完成试点后请对方明确下一次工作的交付物、期限、验收方式与现有预算；可以请其报价或说明内部可批准的范围。对方愿意提供预算但没有付款，应标为“预算讨论”，不能计为客户收入。

如果双方形成明确的付费约定，先确认实际能交付的范围、运营及联系信息、适用的交易与退款安排、收款方式和费用，再由用户决定是否接受并履约。不要预售尚不存在的账号体系、自动全站抓取、历史数据库或真实引用监测功能。

首单成功以可核对的实际付款和按约验收为证据。之后观察下一次真实任务是否继续使用、是否再次付款，以及履约后的净收益。付款截图等交易证据需要脱敏，不公开姓名、账户或订单详情。

## 每轮结束如何决策

- 有真实任务但无人完成修复复测：先查流程、报告可理解性和支持负担，不立即增加功能或订阅套餐。
- 有真实交付但无人愿意为额外价值付费：继续验证用途、采购方和交付范围，保留免费工具，不把试用人数当作商业成功。
- 发生付款但交付成本超过收入：记录成本，调整范围或流程，再验证；收入本身不能证明盈利。
- 有真实付款、按约验收、下一次续用且成本可覆盖：再考虑账户、历史报告、共享限流或计费系统等投入。

建了多少页面、写了多少测试、收到多少表扬都不是本轮商业成功标准。它们可以说明执行进度；商业证据必须来自真实任务、可核对付款、再次使用和包含托管 / API / 支持投入后的收益。
